# Public and LAN OIDC issuer configuration

The desktop chooses an exact OIDC issuer from its own origin. The public desktop
origin `https://xenon.jyxxe.com` uses `https://xenon.jyxxe.com/auth/realms/xeonolab`;
`https://xenon.lan` uses `https://auth.xenon.lan/realms/xeonolab`; direct IP
access at `https://192.168.0.101:9443` keeps the existing
`https://192.168.0.101:9444/realms/xeonolab` issuer. These mappings are generated
in each service configuration by `scripts/prepare_deployment.py`. The generated
token endpoint map follows each exact issuer.

Each service validates JWT issuer against the legacy `OIDC_ISSUER` plus only the
explicit values in `OIDC_ISSUERS_BY_ORIGIN_JSON`. The desktop sends its origin to
`/api/v1/auth/config`; the server accepts only the configured browser origins.
The browser verifies that discovery's issuer is an exact match and that the
authorization, token, and JWKS URLs remain under that issuer's HTTPS origin and
realm path. The server binds code exchange and refresh to the selected issuer,
checks the signed token's issuer, audience, expiry and subject, and stores the
issuer in a separate `session_issuers` table keyed by session id. The original
five-column `sessions` table stays unchanged, so an older release can still use
its positional five-value insert during rollback. At startup, rows without a
side-table entry are assigned the legacy `OIDC_ISSUER`; reads also fall back to
that issuer. Existing IP sessions therefore continue to refresh during staged
migration and rollback. PKCE S256, state, exact callback origin, account
authorization, and offline-session behavior remain required.

## Required operator configuration

Before applying this change, verify the following deployment inputs from the
operator-controlled environment; the checked-in addresses are examples of the
current intended topology and are not evidence of live DNS, TLS, routing, or
firewall state:

- The public auth hostname, desktop origins, LAN auth hostname, and direct IP
  issuer all resolve or route to the intended Keycloak service and present a
  certificate trusted by the respective browser and desktop API service.
- The public Tunnel sends the desktop host to `cloudflare-origin.caddy`. Its
  `/auth/` handler strips that prefix to the Keycloak root and explicitly sends
  `X-Forwarded-Prefix: /auth`, the original `X-Forwarded-Host`, and
  `X-Forwarded-Proto: https`. The auth subdomain route is not the selected public
  issuer. The desktop auth callback stays on the desktop origin; the realm
  redirect URI list contains only the three exact root callbacks.
- Keycloak 26.7.2 derives frontend URLs from trusted forwarded host/proto
  headers. With multiple external names, its static `KC_HOSTNAME` must be unset
  and `KC_HOSTNAME_STRICT=false`; retain `KC_PROXY_HEADERS=xforwarded` and set
  `KC_PROXY_TRUSTED_ADDRESSES` to the Web 101 proxy address. The Keycloak HTTP
  listener on VM 109 must be reachable only from the Web 101 Caddy proxy. Do not
  expose that listener through the Tunnel or a public firewall. Keycloak warns
  that dynamic hostnames are safe only when the proxy overwrites Host and is
  trusted; see its [hostname](https://www.keycloak.org/server/hostname) and
  [reverse proxy](https://www.keycloak.org/server/reverseproxy) guidance.
- VM 101 can reach every endpoint in `OIDC_TOKEN_URLS_JSON` with TLS validation
  enabled. Token URL entries must use the same HTTPS host, port and realm path
  as their issuer; do not redirect token requests to an unrelated endpoint or
  change the URL host independently of the token issuer. The reviewed
  VM-local route in [`oidc-backchannel.md`](oidc-backchannel.md) optionally
  resolves the public host to VM101's loopback Caddy vhost, preserving the URL
  hostname and TLS verification while avoiding VM101's outbound public round
  trip. The runbook is not evidence that the route has been applied or that
  public egress caused an observed failure.
- API services receive the exact issuer-origin and issuer-token URL JSON maps
  generated by `scripts/prepare_deployment.py`. Keep the existing IP issuer as
  `OIDC_ISSUER` during migration so old session rows and the rollback path retain
  their known issuer.

Never put client secrets, signing private keys, or tokens in these maps or in
source control. The existing `OIDC_PUBLIC_KEY`, audience, CA, and private
credential-file handling remain separate.

## Staged apply and rollback

This change has not been applied to production. An authorized operator should
first take protected, restorable copies of the current Keycloak environment and
realm files, Web 101 service configuration, and the relevant service
configuration files. Do not print secret-bearing files into a terminal log.

1. Save protected, restorable copies of the six current service env files before
   staging. Run the normal `scripts/stage_release.py` path. It extracts only
   `OIDC_ISSUERS_BY_ORIGIN_JSON` and `OIDC_TOKEN_URLS_JSON` from the generated
   desktop-web env file, sends that map-only payload to the fixed service nodes,
   and atomically updates those two variables in `desktop-web`, `xelibrary`,
   `tool-gateway`, `llm-gateway`, `embedding`, and `dev-agent`. All other env
   entries and file ownership/mode are preserved. Each file replacement is
   atomic, but the six files and multiple nodes are not one transaction. If any
   staging step fails, do not activate: rerun staging to completion or restore
   the saved configuration snapshots first. Staging does not restart services;
   activation restarts them on the new release. Verify each health check and
   confirm that JWTs from the existing IP issuer still pass while an
   unconfigured issuer is rejected.
2. On the separate Auth 109 deployment, apply the dynamic-host Keycloak
   configuration and exact realm callback URIs through the authorized operator
   process, then restart Keycloak. This VM is outside the generic application
   activation target list and must be handled separately.
3. From a clean browser, verify public discovery advertises issuer
   `https://xenon.jyxxe.com/auth/realms/xeonolab` and its endpoints stay under
   that `/auth` prefix. Complete Authorization Code + PKCE login, session
   exchange, restore, refresh and logout through the public desktop. Repeat from
   `xenon.lan` and direct IP. Check signed `iss` claims, callback exactness,
   browser origin, TLS, and API authorization at each entry point. A static
   discovery fetch alone does not constitute login acceptance.
4. Roll back by restoring the saved Keycloak environment and realm configuration
   first, restarting Auth 109, then restoring the saved six service env files
   and previous application release through the authorized release process.
   Restore env files with their original root ownership and permissions, then
   restart the affected services. Existing IP-issued sessions remain usable.
   Sessions created under a public or LAN alias may require users to sign in
   again after rollback; do not loosen issuer checks to preserve them.

Do not remove the explicit legacy IP issuer from service validation until the
operator has verified session migration/expiry and approved a separate cleanup.
No live discovery, browser, Keycloak, firewall or production acceptance was
performed as part of this local implementation.
