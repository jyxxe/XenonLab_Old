# Public and LAN OIDC issuer configuration

The desktop chooses an exact OIDC issuer from its own origin. The public desktop
origin `https://xenon.jyxxe.com` uses `https://xenon.jyxxe.com/auth/realms/xeonolab`;
`https://xenon.lan` uses `https://auth.xenon.lan/realms/xeonolab`; direct IP
access at `https://192.168.0.101:9443` keeps the existing
`https://192.168.0.101:9444/realms/xeonolab` issuer. These mappings are generated
in each service configuration by `scripts/prepare_deployment.py`. The generated
token endpoint map follows each exact issuer.

Each service validates JWT issuer against the legacy `OIDC_ISSUER` plus only the
explicit values in `OIDC_ISSUERS_BY_ORIGIN_JSON`. The desktop sends its origin to
`/api/v1/auth/config`; the server accepts only the configured browser origins.
The browser verifies that discovery's issuer is an exact match and that the
authorization, token, and JWKS URLs remain under that issuer's HTTPS origin and
realm path. The server binds code exchange and refresh to the selected issuer,
checks the signed token's issuer, audience, expiry and subject, and stores the
issuer in a separate `session_issuers` table keyed by session id. The original
five-column `sessions` table stays unchanged, so an older release can still use
its positional five-value insert during rollback. At startup, rows without a
side-table entry are assigned the legacy `OIDC_ISSUER`; reads also fall back to
that issuer. Existing IP sessions therefore continue to refresh during staged
migration and rollback. PKCE S256, state, exact callback origin, account
authorization, and offline-session behavior remain required.

## Required operator configuration

Before applying this change, verify the following deployment inputs from the
operator-controlled environment; the checked-in addresses are examples of the
current intended topology and are not evidence of live DNS, TLS, routing, or
firewall state:

- The public auth hostname, desktop origins, LAN auth hostname, and direct IP
  issuer all resolve or route to the intended Keycloak service and present a
  certificate trusted by the respective browser and desktop API service.
- The public Tunnel sends the desktop host to `cloudflare-origin.caddy`. Its
  `/auth/` handler strips that prefix to the Keycloak root and explicitly sends
  `X-Forwarded-Prefix: /auth`, the original `X-Forwarded-Host`, and
  `X-Forwarded-Proto: https`. The auth subdomain route is not the selected public
  issuer. The desktop auth callback stays on the desktop origin; the realm
  redirect URI list contains only the three exact root callbacks.
- Keycloak 26.7.2 derives frontend URLs from trusted forwarded host/proto
  headers. With multiple external names, its static `KC_HOSTNAME` must be unset
  and `KC_HOSTNAME_STRICT=false`; retain `KC_PROXY_HEADERS=xforwarded` and set
  `KC_PROXY_TRUSTED_ADDRESSES` to the Web 101 proxy address. The Keycloak HTTP
  listener on VM 109 must be reachable only from the Web 101 Caddy proxy. Do not
  expose that listener through the Tunnel or a public firewall. Keycloak warns
  that dynamic hostnames are safe only when the proxy overwrites Host and is
  trusted; see its [hostname](https://www.keycloak.org/server/hostname) and
  [reverse proxy](https://www.keycloak.org/server/reverseproxy) guidance.
- VM 101 can reach every endpoint in `OIDC_TOKEN_URLS_JSON` with TLS validation
  enabled. Token URL entries must use the same HTTPS host, port and realm path
  as their issuer; do not redirect token requests to an unrelated endpoint or
  change the URL host independently of the token issuer. The reviewed
  VM-local route in [`oidc-backchannel.md`](oidc-backchannel.md) optionally
  resolves the public host to VM101's loopback Caddy vhost, preserving the URL
  hostname and TLS verification while avoiding VM101's outbound public round
  trip. The runbook is not evidence that the route has been applied or that
  public egress caused an observed failure.
- API services receive the exact issuer-origin and issuer-token URL JSON maps
  generated by `scripts/prepare_deployment.py`. Keep the existing IP issuer as
  `OIDC_ISSUER` during migration so old session rows and the rollback path retain
  their known issuer.

`OIDC_ROLE_SCOPES_JSON` is generated from the single checked-in policy in
`xeonolab.role_scopes.OIDC_ROLE_SCOPES`. The staging helper exports that exact
mapping and rejects payloads that differ from the shared policy; it updates
only the two issuer maps and this role-map variable in each service env, while
preserving all other entries and file metadata.

## Realm roles and account-tree adoption

The shared policy defines two realm roles. `platform-admin` keeps the full
scope set; `embedding-admin` maps to `desktop:read embedding:read
embedding:write` so an operator can provision an Embedding administrator by
assigning that realm role in Keycloak. Assigning a realm role only takes effect
after the guarded role-map rollout above has staged and loaded the updated
`OIDC_ROLE_SCOPES_JSON` in every service.

Realm roles never widen a registered managed account: identities registered in
the account tree resolve their effective scopes from account grants only, and
a root's grants are the snapshot taken at bootstrap. When a release adds new
scopes to a role (theorem scopes in the original policy, embedding scopes
later), existing roots must explicitly adopt them before children can be
granted them: sign in as the human root, open the account panel on the root
account where `root-scope-candidates` lists the not-yet-adopted scopes, save
the updated grants, then grant the scopes to child accounts. Grant requests
that exceed the parent tree fail with `PERMISSION_ESCALATION`, which names the
exact scopes that are not grantable. Never widen a role map to work around a
missing adoption.

Never put client secrets, signing private keys, or tokens in these maps or in
source control. The existing `OIDC_PUBLIC_KEY`, audience, CA, and private
credential-file handling remain separate.

## Staged apply and rollback

This change has not been applied to production. An authorized operator should
first take protected, restorable copies of the current Keycloak environment and
realm files, Web 101 service configuration, and all seven affected service env
files, explicitly including `/etc/xeonolab/deploy-gateway.env`. Do not print
secret-bearing files into a terminal log.

1. **Protected release boundary:** the normal DevAgent protected-release path
   uses the fixed `infra/devagent/stage_receiver.py` to stage an immutable
   application archive and dependencies. It does not install or update
   `/etc/xeonolab/*.env`; activation restarts services but leaves those external
   environment files unchanged. A role-map change therefore requires a
   separately reviewed and guarded root configuration rollout with protected
   backups, exact shared-policy validation, atomic per-file replacement,
   service health checks, and a tested restore path. Do not assume this helper
   or an application release updates production role grants, and do not extend
   the fixed staging receiver to perform root config writes.

   The separate `scripts/stage_release.py` operator helper can stage the
   generated issuer maps and shared role map into service env files when it is
   explicitly selected by that approved configuration procedure. It updates
   only `OIDC_ISSUERS_BY_ORIGIN_JSON`, `OIDC_TOKEN_URLS_JSON`, and
   `OIDC_ROLE_SCOPES_JSON` in `desktop-web`, `xelibrary`, `deploy-gateway`,
   `tool-gateway`, `llm-gateway`, `embedding`, and `dev-agent`; all other env
   entries and file ownership/mode are preserved. Each replacement is atomic,
   but the seven files and multiple nodes are not one transaction. Save
   protected restorable copies first. If any step fails, do not activate; rerun
   staging to completion or restore all saved snapshots. Staging does not
   restart services, so a successful stage alone does not mean running
   processes have loaded the role map. The normal protected activation restarts
   its configured application services (desktop-web, xelibrary, tool-gateway,
   llm-gateway, embedding and dev-agent), but deliberately excludes
   deploy-gateway. After the protected deployment reaches `completed`, the
   fixed deployment runner invokes `devagent-stage gateway <approved-sha>
   <deployment-id>` while the same deployment lease remains active. Its
   `restart_gateway` guard requires the matching terminal deployment and
   approved release, restarts deploy-gateway, then checks
   `http://192.168.0.106:8103/health/ready`. Count the role map as loaded only
   after that guarded restart and readiness check succeed, along with the
   configured application service health checks. Confirm JWTs from the
   existing IP issuer still pass while an unconfigured issuer is rejected.
2. On the separate Auth 109 deployment, apply the dynamic-host Keycloak
   configuration and exact realm callback URIs through the authorized operator
   process, then restart Keycloak. This VM is outside the generic application
   activation target list and must be handled separately.
3. From a clean browser, verify public discovery advertises issuer
   `https://xenon.jyxxe.com/auth/realms/xeonolab` and its endpoints stay under
   that `/auth` prefix. Complete Authorization Code + PKCE login, session
   exchange, restore, refresh and logout through the public desktop. Repeat from
   `xenon.lan` and direct IP. Check signed `iss` claims, callback exactness,
   browser origin, TLS, and API authorization at each entry point. A static
   discovery fetch alone does not constitute login acceptance.
4. Roll back by restoring the saved Keycloak environment and realm configuration
   first, restarting Auth 109, then restoring all seven saved service env files,
   including `deploy-gateway.env`, and the previous application release through
   the separately authorized recovery process. Restore the original file owner,
   group and mode. Have the operator's guarded recovery flow restart every
   affected service and verify readiness; restoring files alone does not reload
   a running process. Existing IP-issued sessions remain usable.
   Sessions created under a public or LAN alias may require users to sign in
   again after rollback; do not loosen issuer checks to preserve them.

Do not remove the explicit legacy IP issuer from service validation until the
operator has verified session migration/expiry and approved a separate cleanup.
No live discovery, browser, Keycloak, firewall or production acceptance was
performed as part of this local implementation.

## Forwarded host must keep the port

Keycloak derives the advertised issuer from the trusted `X-Forwarded-Host`
header. Caddy's `{host}` placeholder strips the port, while
`{http.request.hostport}` keeps it (and equals the plain host for default-port
hosts). Both edges must therefore send:

```caddyfile
header_up X-Forwarded-Host {http.request.hostport}
header_up X-Forwarded-Proto https
```

Observed failure (2026-10-22): after the operator-managed LAN include was synced
with `header_up X-Forwarded-Host {host}`, a direct-IP request to
`https://192.168.0.101:9444` made Keycloak advertise
`https://192.168.0.101/realms/xeonolab`. The deploy gateway validates the exact
`OIDC_ISSUER=https://192.168.0.101:9444/realms/xeonolab`, so release creation
returned `401 Unauthorized` and the deployment failed in the preflight/staging
phase before any gateway record existed. Restoring `{http.request.hostport}` and
reloading Caddy made discovery advertise the ported issuer again.

After any Caddy change on either edge, verify the issuer before publishing:

```sh
curl -sS -k https://192.168.0.101:9444/realms/xeonolab/.well-known/openid-configuration \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["issuer"])'
# must print https://192.168.0.101:9444/realms/xeonolab
```

The public edge is covered by activation; the LAN include is operator-synced, so
this check belongs to the LAN sync procedure in
[`cloudflare-caddy-include.md`](cloudflare-caddy-include.md).
