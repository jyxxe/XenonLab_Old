# Issue 159 — Typed exact field filters

Verified against integration baseline `2aabf623aa88f68c0050774ddb03f2773681abfe` using temporary local tables, a synthetic development identity and actual API/browser behavior. This document describes the typed-filter rules, regression coverage and known precision boundary for Issue #159.

Rules: numeric-looking input, JSON strings/arrays/objects and the exact literals true/false/null retain JSON types. Ordinary unquoted text remains a string. Numeric-looking strings and text beginning with digits must use JSON double quotes, e.g. `confidence = "0.91"`; `confidence = 0.91` sends a number. Invalid typed syntax, non-finite numbers and integer-valued numbers outside JavaScript's safe integer range report a field-specific validation message. Unsafe numeric values are rejected rather than silently rounded or serialized as null. Nested JSON numbers receive the same checks. Arrays/objects follow the existing API's exact-value comparison; no schema guessing is performed for global search.

The parser returns typed values through its declaration and useSearch override type. Any parser error blocks the entire search before API submission, including mixed valid/invalid conditions. Inline errors have alert semantics; editing to valid input permits an ordinary retry. Backend comparison, routes, permissions and stored data are unchanged. Own field names are constructed through Object.fromEntries, preserving normal duplicate-field last-value behavior.

Independent of #158: edits to hooks are only its override type and parse-error guard; SearchView edits are only input help/placeholder/error alert. No replacement of the session/scroll code, no Inspector edit or dependency on #153. Integrating with #158 must preserve its resultVersion and controlled showFilters additions. There is no numeric backend coercion. Numeric filters beyond the browser's safe integer range are deliberately unsupported with an explicit error; quoting produces a string and does not claim to match a numeric field.
